# Sendikko Threat Model & Security Posture

| Threat Category | Potential Attack Vector | Impact | Mitigation in Sendikko |
| :--- | :--- | :--- | :--- |
| **Data Confidentiality** | Compromise of Telegram channel or Bot token | Attacker gains access to stored raw chunk blobs | **Client-side AES-256-GCM zero-knowledge encryption**. All chunk data is encrypted in the browser before transmission. The key exists only in URL fragment `#k=...` or user password. Telegram stores only ciphertext. |
| **Data Confidentiality** | Compromise of Database (Metadata leakage) | Attacker accesses chunk mappings, file IDs, and verifiers | `tg_file_id` is encrypted at rest using `CHUNK_ENC_KEY` (AES-256-GCM). File names and MIME types can be client-encrypted (`name_enc`, `mime_enc`). Password verifiers are one-way hashed with independent salts. |
| **Integrity & Reordering** | Attacker tampers with chunks or swaps chunk order | Corrupted files delivered to recipient or malicious payload assembly | Unique random 96-bit IV per chunk + **Chunk Index bound as Additional Authenticated Data (AAD)** in AES-GCM. Each chunk has a SHA-256 checksum validated upon download. Any alteration causes GCM auth tag failure. |
| **Authentication & AuthZ** | IDOR (Insecure Direct Object Reference) on file operations | Unauthorized user renames, downloads, or deletes another user's file | Strict ownership checks (`owner_id === req.user.id`) enforced on all mutating routes (`PATCH`, `DELETE`, `POST /regenerate-code`). Unauthenticated download routes check public file status and password verifier. |
| **Session Security** | XSS stealing session tokens | Account takeover | Short-lived access JWT (15m) + rotating refresh token stored in `httpOnly`, `Secure`, `SameSite=Strict` cookies. Strict Content Security Policy (CSP) blocking inline scripts and unauthorized origins. |
| **Brute Force (Password)**| Attacker attempts dictionary attack on password-protected file | File decryption | Server-side rate limiting per IP and per file code. Locked after 5 consecutive incorrect attempts with exponential cooldown. Constant-time comparisons (`crypto.timingSafeEqual`) prevent timing side channels. |
| **Brute Force (Codes)** | Automated scraping of 8-character codes | Harvesting random files | Unambiguous 8-character alphabet (31 characters: `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`, excluding `0, O, 1, I, l`). Yields $31^8 \approx 852$ billion combinations. Strict IP rate limiting on code lookups. |
| **Denial of Service** | Flooding backend with chunk uploads or huge files | Resource exhaustion / crash | Configurable per-user quota (e.g. 10 GB), request size limits (25 MB max per chunk request), streaming directly to Telegram without buffering full files in memory. |
| **Telegram Rate Limits** | Sudden burst of uploads triggering Telegram 429 Too Many Requests | Upload failure / stalled requests | Server honors Telegram `retry_after` header, queues chunk dispatches, uses exponential backoff with jitter, and limits concurrent uploads to 3 per file session. |
| **Stale Data / Privacy** | Deleted files lingering on Telegram | Leaked remnants | Soft delete moves file to trash (7 days). Permanent delete triggers queue to call Telegram `deleteMessage` for every chunk. Nightly cron job purges expired files and abandoned uploads. |
| **Malicious Content** | Distribution of executables / malware | Recipient infection | Files are served with `Content-Disposition: attachment; filename="..."` and `X-Content-Type-Options: nosniff`. Safe previewing only via isolated/sandboxed sandboxed renderers. Optional executable file extension blocklist hook. |
| **Client Privacy** | Server tracking user identities and download IP addresses | User deanonymization | Server computes salted SHA-256 hashes of client IP and User-Agent (`ip_hash`, `ua_hash`). Raw IP addresses are never persisted in database logs. |
